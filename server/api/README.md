# @mykids/api

Сервер семьи: источник истины по балансам, политикам и начислениям.

```bash
# Нужен Postgres. Локально:
createdb mykids && createdb mykids_test
cp .env.example .env

npx prisma migrate deploy
npm run dev            # http://localhost:3000
npm test               # 124 теста против настоящей базы
```

## Зачем он нужен

До сервера три готовых куска не были соединены: раннер считал кредиты в
`localStorage`, который ребёнок может отредактировать из консоли, а агент читал
политику из локального файла. Теперь решения принимает сервер, а клиенты
считают то же самое лишь для того, чтобы сразу показать результат.

## Слои

| Модуль | Отвечает за |
|---|---|
| `prisma/schema.prisma` | Схема базы; `LedgerEntry` только дополняется |
| `services/ledger.service.ts` | Свёртка баланса, сводка за сутки, дедупликация синка |
| `services/economy.service.ts` | Выдача, обмен, начисление за задания, покупки |
| `services/auth.service.ts` | Пароль argon2, TOTP, токены устройств |
| `routes/` | HTTP: админка, ребёнок, агент |

## Решения

**Балансы нигде не хранятся изменяемым полем.** Считаются свёрткой журнала через
`@mykids/domain`. Для семьи это тысячи строк в год — свёртка дешевле, чем разбор
рассогласования между счётчиком и историей после офлайн-синхронизации.

**Суточные потолки идут по `recordedAt` — часам сервера.** `occurredAt` приходит
с устройства и может быть подкручен: считай по нему, перевод часов назад открывал
бы новый «день» и обнулял антифарм-лимиты.

**Уникальность пары устройство+счётчик.** Повторная отправка очереди агента после
обрыва связи не удваивает списание. Записи сервера идут без `deviceId` и под это
правило не подпадают — в Postgres NULL-ы в уникальном индексе различны.

**Цена покупки списывается сразу, в том числе у товаров на одобрение.** Иначе те
же кредиты можно потратить дважды, пока родитель думает. Одобрение выдаёт
эффект, отклонение возвращает цену отдельной строкой журнала
(`purchase_refund`). До этого очередь покупок была тупиком: цена списывалась,
а разобрать покупку было нечем.

**Решение по очереди — условным обновлением.** Статус попытки или покупки
меняется, только если она всё ещё ждёт: проверка и запись — два шага, и
двойной щелчок иначе проходил бы оба раза. Решать может только родитель с
правами на запись — раньше подтверждать задания мог и наблюдатель.

**Сохранение правил не трогает белый список агента.** Админка его не
редактирует; раньше она присылала пустой список, и первая же правка лимитов
стирала `explorer.exe` и сам агент из «всегда разрешённого».

**Пятисотые пишутся в журнал.** `LOG_LEVEL` (по умолчанию `warn`); наружу
уходит только общая фраза. Ошибки разбора запроса приходят фразой с полем, а
не дампом zod.

**Попытка и запись журнала создаются одной транзакцией.** Иначе кредиты окажутся
начислены без следа о том, за что.

**Асимметрия офлайна.** `POST /agent/usage` принимает списание постфактум — иначе
отключение Wi-Fi давало бы бесконечное время. Начисление за задания идёт только
через `/child/attempts`, где сумму назначает сервер.

**`/child/attempts` принимает только сам ответ.** Раньше страница присылала с
ним и свою оценку, и цену задания, и потолок пакета, и cooldown — то есть
ребёнок называл себе цену сам, и весь антифарм обходился одним запросом мимо
страницы. Пакеты сервер отдаёт со своего диска, значит, и правильный ответ, и
цену он может прочитать там же: этим занят `services/content.service.ts`,
проверяет ответ `@mykids/task-runner/grade`. То же правило, что и с помощником
на Windows: смотреть не на то, что говорят, а на то, что видно самому.

Остаётся ровно одно, что принимается на слово: результат виджета у заданий типа
`interactive` — считает его браузер, и заменить это нечем. От него защищает
`minDurationSec` в самом задании, а не сервер.

**Пакет должен быть назначен ребёнку.** Иначе кредиты приносил бы любой пакет из
каталога, включая снятые родителем.

**Задания типа `parent_verified` не платят сами по себе.** «Прибрался в комнате»
машиной не проверить, и сервер раньше просто верил — а таких заданий в пакетах
больше половины. Теперь попытка встаёт в очередь со статусом `pending_approval`,
и кредиты назначаются в момент подтверждения родителем, по цене из пакета и
сегодняшним потолкам. Подтверждение снимает только то условие, которое сервер
проверить не мог, а не правила экономики: упёршись в дневной потолок, задание
остаётся в очереди до завтра, а не закрывается нулём.

**Токены хранятся хешем.** Утечка базы не должна давать ни вход в аккаунт
родителя, ни возможность выдать себя за агента.

**Неверный адрес и неверный пароль дают одну ошибку**, и хеш считается даже для
несуществующего адреса — иначе форма входа становится способом узнать, кто
зарегистрирован.

**Ребёнку отдаются его правила, а не только баланс.** Скрытая механика в 11-13 лет
воспринимается как несправедливость и провоцирует искать обход вместо игры по
правилам.

## Почему Fastify, а не NestJS

В плане был NestJS. Монорепа собрана на строгом ESM с `verbatimModuleSyntax`, а
декораторы NestJS тянут CommonJS и отдельный tsconfig. Для API такого размера
модульная система и DI не окупают этого трения. Маршруты — обычные функции,
валидация — zod, те же схемы, что и в домене.

## Карта маршрутов

| Группа | Доступ | Назначение |
|---|---|---|
| `/auth/*` | открыт / сессия | Регистрация, вход, TOTP, приглашение родителей |
| `/admin/*` | сессия родителя | Дети, политики, журнал, устройства, магазин, одобрения |
| `/child/*` | токен устройства | Баланс и правила, задания, обмен, магазин |
| `/agent/*` | токен устройства | Синхронизация политики, отправка расхода, события вмешательства |
